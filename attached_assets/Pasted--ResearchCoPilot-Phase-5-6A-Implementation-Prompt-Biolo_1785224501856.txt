## 2. Phase Goal
 
Researchers frequently need to answer a more fundamental question than "what does this variant mean" or "what protein does this transcript encode": **what does this gene/protein actually do inside the cell?**
 
This phase exists to answer that question directly, using the biological community's own standard vocabulary (Gene Ontology) rather than inventing a new one. It is deliberately sequenced ahead of Domains (5.7) and Structures (5.8) because researchers conceptually ask "what does it do" before "what does it look like" — function before form. Without this phase, a researcher has identifier and variant context but no answer to the most basic biological question about the gene they're looking at.

## 5. Implementation Roadmap
 
### Stage 1 — Parser
 
 
- If the audit (Section 3) confirmed Gene XML sufficiency: extend the existing Gene EFetch XML parser to extract GO annotations (`goId`, `term`, `aspect`, `evidenceCode`) alongside the fields it already extracts. Do not build a separate parser file that duplicates existing XML traversal logic — extend the existing one.
 
- If a fallback source is later architecturally approved following Section 3's audit, implement a new isolated parser for gene2go or QuickGO responses, following the existing parser conventions used in Phase 5.5 (same error handling, same return shape conventions) so it's a drop-in sibling, not a stylistic outlier.
 
- In either case, the parser must never fabricate a GO term, evidence code, or annotation. If the source returns nothing, the resulting list is empty — not padded, not defaulted.
 

 
### Stage 2 — Data Model
 
Implement exactly the following interfaces (from the approved design spec — do not modify field names or types):
 `interface FunctionalAnnotation {     goId: string;                    // e.g. "GO:0006915" — CANONICAL identifier, never the term name     term: string;                    // e.g. "apoptotic process" — DISPLAY LABEL ONLY     aspect: "biological_process" | "molecular_function" | "cellular_component";     evidenceCode: string;            // GO Consortium's own standard codes (e.g. IEA, TAS, EXP) — preserved as-is     evidenceLabel: string;           // human-readable expansion, e.g. "Inferred from Electronic Annotation"     source: "ncbi-gene-xml" | "gene2go" | "quickgo"; // whichever Section 3's audit confirmed     geneId: string;     geneSymbol: string;     organism: string;   }   ` 
Build the `evidenceCode` → `evidenceLabel` normalization **once**, at the data layer (e.g. a single lookup table consumed by the parser/model layer), not re-implemented inside individual UI components. Use GO's own published evidence code taxonomy — do not invent a ResearchCoPilot-specific confidence score.
 
`PathwayMembership` (Reactome/WikiPathways) is defined in the design spec for forward reference only. **Do not implement it in this phase** — it belongs to 5.6B (see Section 10, Out of Scope).
 
### Stage 3 — API / Retrieval Layer
 
 
- Wire the parser output into whatever retrieval path Section 3's audit confirmed (extended Gene EFetch call, or new `gene2go`/QuickGO call).
 
- Reuse the existing caching layer from Gene Explorer if the data source is the same Gene XML; do not build a second cache.
 
- If a new source was required (and has been architecturally approved per Section 3), implement caching consistent with existing patterns. **Cache by the resolved GeneID (or the repository's existing gene cache namespace) — not by `goId` alone.** A GO ID identifies an ontology term, not a gene's annotation set; the same GO ID (e.g. `GO:0006915`) can legitimately apply to many different genes (TP53, CFTR, etc.), so caching keyed only on `goId` would return the wrong gene's annotations. `goId` remains the canonical identifier for `FunctionalAnnotation` objects and relationships (Section 7), but it is not sufficient as a retrieval cache key on its own.
 
- If the source returns multiple annotations sharing the same `goId` but differing by `evidenceCode` (e.g. one `EXP` and one `IEA` annotation for the same term), preserve each one distinctly — do not deduplicate by `goId`. Only collapse entries if the source itself has already aggregated them upstream; do not invent custom deduplication rules.
 

 
### Stage 4 — UI
 
 
- Display annotations grouped into three collapsible sections by `aspect`: Biological Process, Molecular Function, Cellular Component. Do not render a flat list.
 
- Each group shows its item count in the group header.
 
- Each row displays: `term` (display label), `evidenceCode` with `evidenceLabel` shown on hover/expansion, and enough visual distinction that IEA (computational) annotations are visibly distinguishable from experimentally-derived ones (e.g. EXP, TAS) — without hiding or filtering out IEA-only annotations.
 
- Reuse existing loading-state and empty-state components from Phase 5.5 rather than building new ones.
 

 
### Stage 5 — Integration
 
 
- Integrate the Functional Annotation section into the existing Gene/Protein context view, consuming the already-resolved identifiers per Section 7.
 
- Confirm the section still renders correctly with full Gene/Transcript/Protein context when deep-linked to directly (Section 10 of the design spec — context-awareness rule).

## 7. Identifier Immutability
 
This rule is permanent and applies to every phase, including this one:
 
**No module in this phase may independently resolve gene, transcript, protein, or organism identity.** This phase always consumes identifiers already resolved by Phase 5.2 (Gene Explorer) and earlier explorers.
 
Additionally, specific to this phase's data model: `goId` (e.g. `GO:0006915`) is the canonical identifier for all internal keys, cache keys, and relationships. `term` (the human-readable GO name) is a **display label only** and must never be used as an identifier anywhere — GO term names are occasionally revised by the GO Consortium, while GO IDs are stable. This mirrors the identical discipline already applied to GeneID, transcript accessions, and ClinVar VCV IDs.
  
## 8. Performance Requirements
 
 
- Minimize API calls: if Section 3's audit confirms Gene XML sufficiency, this phase must add **zero** new external API calls beyond what Gene Explorer already performs.
 
- If a new source is required, cache aggressively using existing cache infrastructure, keyed by the resolved GeneID (or existing gene cache namespace) — never by `goId` alone (a GO ID identifies an ontology term shared across many genes, not a specific gene's annotation set) and never by `term`.
 
- Apply pagination/lazy loading to any aspect group whose count is large enough to warrant it (genes can have 50–100+ annotations) — reuse the existing Universal Pagination Framework rather than building bespoke pagination.
 
- Do not eagerly fetch full annotation detail for every term if the source supports a cheaper summary-level call; fetch summary-level data (term, aspect, evidence code) by default.
 
- Avoid duplicate requests for the same gene across the session — rely on existing caching to prevent this.
 

  
## 9. Error Handling
 
Specify and implement graceful degradation for:
 
 
- **Empty data**: gene has no GO annotations at all → show an explicit empty state per aspect group, not a broken/blank section.
 
- **Unsupported organisms**: if the organism isn't covered by the data source, show a clear "not available for this organism" message rather than a silent failure — note GO does cover many non-human model organisms, so this should be rarer than in Phase 5.5's clinical-data case, but must still be handled.
 
- **API failures**: if the retrieval call fails (whichever source Section 3 confirmed), show a retry-capable error state consistent with existing error-handling patterns from 5.5.
 
- **Malformed identifiers**: should not reach this phase given identifier immutability (Section 7), but defensively handle a malformed/missing `goId` by excluding that row rather than crashing the group.
 
- **Rate limiting**: if hitting a new external source, respect and surface rate-limit backoff consistent with existing patterns used for other NCBI/EBI calls in this project.
 
- **Unavailable annotations for a specific aspect**: if a gene has annotations in only one or two of the three aspects, show the populated groups and an explicit "no annotations found" state for the empty ones — do not hide the empty aspect groups entirely, since their absence is itself informative.
 

 
The UI must always degrade gracefully; it must never hard-fail the entire Gene/Protein context view due to a Functional Annotation retrieval issue.
  
## 10. Out-of-Scope List (This Phase Only)
 
Explicitly excluded from 5.6A:
 
 
- **Pathway data of any kind** — Reactome and WikiPathways integration is 5.6B, not this phase. Do not implement `PathwayMembership` retrieval or display here.
 
- **KEGG** — not justified by default under current licensing terms; excluded entirely unless a separate legal/licensing review clears it (5.6B's job, not 5.6A's).
 
- **Pathway diagram/graph visualization** — out of scope for the entire 5.6 phase, closer to Structures (5.8) or a future effort.
 
- **Disease/drug-target implications** of functional annotations — that's Phase 5.9.
 
- **Any LLM-generated interpretation** of biological function — display only what the source provides.
 
- **Standalone GO-term search** — unlike Variant Explorer's deliberate rsID exception, this phase's data is only reached downstream of an already-resolved gene/protein; there is no standalone entry point.
 
- **Hardening, cross-species end-to-end validation, and the `v5.6-complete` tag** — that is 5.6C's job, after 5.6B is also complete.
