PHASE 5.7B — PROTEIN DOMAINS HARDENING
(Validation of the 5.7A architecture as actually implemented — no new
functionality)

PROJECT CONTEXT — READ FIRST

Fetch from the remote and verify repository state before making any
changes. Confirm all 5.7A work is present on origin/main before
starting (git log -1 --oneline; git ls-remote origin main — both must
match).

This phase hardens the architecture actually built in 5.7A:

- ProteinIdentifierResolver (lib/protein/identifier-resolver.ts) —
  RefSeq → UniProt resolution via the UniProt ID Mapping API, with a
  deterministic multi-mapping rule (exactly 1 reviewed entry →
  resolved; 2+ reviewed → ambiguous; 0 reviewed → unresolved), its own
  cache (protein-id-map:{refseqAccession}, 24h TTL), and its own rate
  limiter, independent of NCBI/Reactome/InterPro.
- ProteinDomainService (lib/protein/domain-fetch.ts) — InterPro REST
  client consuming the resolved UniProt accession, with its own cache
  (proteindomain:{proteinAccession}, keyed by RefSeq, 24h TTL),
  pagination, and no deduplication of distinct signatures.
- The Protein Domains UI section in GeneExplorerSection, with
  deterministic ordering and two distinct empty states (identifier
  unresolved vs. resolved-but-no-domains).

This is a hardening phase per the project's Phase Pattern
(Foundation → Hardening → Freeze). It adds no new sources, no new
fields, no new UI, and no domain-function interpretation. It performs
validation only, per the Hardening Prompt Pattern already used for
5.3C, 5.4C, 5.5C, and 5.6C.

Explicitly out of scope for this phase (do not implement, even if
tempting mid-session): AlphaFold, PDBe, STRING, BioGRID, structure
visualization, any additional domain data source, new ProteinDomain
fields, new UI sections, or any promotion of ProteinIdentifierResolver
to Frozen Architecture (that decision is deferred to after Phase 5.8
per 5.7A's documented provisional-status rule).

STEP 2 — EDGE CASE VALIDATION

1. Zero domains — a protein that resolves to UniProt successfully but
   has no InterPro annotations. Confirm the "resolved but no domains"
   empty state, not a crash or the unresolved-identifier state.
2. Very large domain set — confirm no truncation, no UI performance
   collapse, and correct deterministic ordering at scale.
3. Overlapping domains — confirm all overlapping signatures from
   different member databases render independently; none are merged,
   truncated, or deduplicated.
4. Non-human proteins — confirm mouse Trp53 (and at least one other
   non-human protein if convenient) resolves and returns domain data
   natively, not through a special-cased path.
5. Malformed/partial InterPro response — confirm graceful degradation
   (skip malformed entries, preserve the rest), not a crash.
6. Pagination — confirm multi-page InterPro responses are fully
   retrieved before normalization, using a protein accession known to
   produce multiple InterPro pages, or an existing controlled
   test/fixture mechanism if one already exists. Do not modify
   production retrieval logic solely to manufacture a multi-page
   case.
7. Domain cache correctness — confirm cache hit on second lookup for
   the same protein (near-zero latency), and that cache entries are
   correctly invalidated after the documented 24h TTL logic (verify
   the TTL check path, not necessarily by waiting 24 real hours).
8. Rate limiter isolation — confirm the InterPro rate limiter and the
   UniProt mapping rate limiter operate independently of each other
   and of NCBI/Reactome/GO limiters; a burst of requests to one does
   not throttle or interfere with another.
9. Deterministic ordering — confirm domains are sorted by
   startPosition ascending, domainName as tiebreaker, null-position
   entries last, and that this ordering is stable across repeated
   requests regardless of the source API's return order.
10. External links — for each displayed domain, confirm the linked
    source record corresponds to the displayed canonical domainId.
    Links must be constructed from domainId, never from domainName.
11. ProteinIdentifierResolver validation — verify independently:
    - a successful mapping returns the expected UniProt accession;
    - a repeated resolution of the same RefSeq accession is served
      from the resolver cache (not re-hitting the UniProt API);
    - an unresolved mapping (0 reviewed entries) produces the
      documented deterministic empty state;
    - an ambiguous mapping (2+ reviewed entries) produces the
      documented deterministic ambiguous state — do not silently pick
      one. If a real biological test case cannot be obtained safely
      against live UniProt data, validate this branch using an
      existing test/mock fixture or controlled response fixture
      instead — do not modify production behavior solely to
      manufacture the case, and do not spend excessive effort
      searching for an exotic real-world protein;
    - resolver cache keys remain based on the canonical RefSeq
      protein accession, never on UniProt accession or protein name.
14. Upstream failure classification — distinguish confirmed empty
    biological results from transient upstream/API failures, for both
    UniProt mapping and InterPro retrieval. A source outage, timeout,
    rate-limit response, or malformed upstream response must never be
    presented to the user as "no domains" — "no domains" and "could
    not retrieve domains" are scientifically and operationally
    different states and must remain distinguishable at both the API
    and UI layers.
12. End-to-end identifier pipeline — confirm a RefSeq protein
    accession is resolved to the expected UniProt accession, that the
    resolved UniProt accession is what's actually sent to InterPro,
    and that the original RefSeq accession remains the canonical
    proteinAccession in the returned ProteinDomain records and in the
    domain cache key. Confirm no code path anywhere substitutes
    UniProt for RefSeq as the internal identifier.
13. Resolver timeout/retry behavior — confirm a mapping timeout or
    transient upstream failure is distinguishable in code from a
    confirmed unresolved mapping (0 reviewed entries), follows the
    implemented poll/retry policy, and is NOT cached as a permanent
    unresolved result — a later retry for the same accession must be
    able to succeed once the transient condition clears.

Run TypeScript after each item; fix immediately if a genuine bug
surfaces (per Implementation Safety Rule 5).
