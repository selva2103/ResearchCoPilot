NON-NEGOTIABLE ARCHITECTURAL CONSTRAINTS

domainId is the canonical identifier everywhere internally (Pfam
PF00870 or InterPro IPR002117) — domainName is display-only, never
used as a key.

uniprotAccession, once resolved, is treated as canonical for the
lifetime of the mapping — never re-derived ad hoc elsewhere in the
codebase. All future InterPro (and later AlphaFold/STRING/etc.) calls
must go through ProteinIdentifierResolver, not re-implement mapping.

ProteinRecord continues to use the RefSeq accession as the project's
canonical protein identifier, exactly as in all prior phases. UniProt
is an external interoperability identifier only, used solely to query
UniProt-dependent external services — it never replaces RefSeq as the
internal key, in caches, in URLs, or in any cross-phase reference.

Never fabricate a domain, accession, position range, or UniProt
mapping — if a source doesn't provide it, the field is null, not
estimated or guessed.

No structure/3D visualization — that's Phase 5.8.

No LLM-generated interpretation of domain function.

InterPro and the UniProt ID Mapping API are both open EBI services —
confirm current terms for both during Step 1 regardless.

Both new external dependencies (UniProt ID Mapping, InterPro) get
their own independent HTTP client, rate limiter, and cache namespace
— same isolation pattern as 5.6B's Reactome/WikiPathways clients, kept
separate from each other and from the NCBI client.

STEP 2 — DATA CONTRACTS (REVISED)

interface ProteinIdentifierMapping {
  refseqAccession: string;
  uniprotAccession: string | null;   // null if unresolved
  reviewed: boolean | null;          // null if unresolved
  resolutionStatus: "resolved" | "unresolved" | "ambiguous";
  source: "uniprot-id-mapping";
}

interface ProteinDomain {
  domainId: string;              // canonical — e.g. "PF00870" or "IPR002117"
  domainName: string;            // display label only
  source: "genpept-features" | "interpro";
  startPosition: number | null;
  endPosition: number | null;
  proteinAccession: string;      // RefSeq accession (project's canonical key)
  uniprotAccession: string;      // resolved UniProt accession used for lookup
  geneId: string;
  organism: string;
}

STEP 3 — RETRIEVAL SERVICES (REVISED)

Build two independent services:

A. ProteinIdentifierResolver
   - Input: RefSeq protein accession.
   - Calls the UniProt ID Mapping API (async job: submit → poll →
     retrieve), applying Step 1's deterministic multi-mapping rule.
   - Polling must use the project's existing retry/backoff policy (the
     same pattern already established for other async or rate-limited
     calls in this codebase). If the mapping job does not complete
     within that policy's bounds, return an explicit temporary-failure
     result — never poll indefinitely, and never treat a timeout as a
     confirmed "unresolved" mapping (a timeout is retryable; an actual
     empty mapping result is not).
   - Own HTTP client, own rate limiter, own cache namespace:
     protein-id-map:{refseqAccession}
   - Cache the full ProteinIdentifierMapping result, including
     unresolved/ambiguous outcomes (so repeated lookups for a
     known-unresolvable protein don't re-hit the API every time).
     Use the project's existing cache TTL policy for this namespace
     unless a TTL is already established specifically for UniProt or
     InterPro data — do not invent a new cache lifetime for this
     phase.
   - Public method returns the full ProteinIdentifierMapping shape,
     not just a bare string, so downstream consumers (this phase and
     future ones) have resolution status and reviewed/ambiguous
     context available without re-deriving it.

B. ProteinDomainService (InterPro client)
   - Consumes ProteinIdentifierResolver's output — never calls UniProt
     mapping itself.
   - Own HTTP client, own rate limiter, own cache namespace:
     proteindomain:{proteinAccession}, using the same existing cache
     TTL policy referenced above.
   - If pagination applies, retrieve all pages before normalization.
     Document observed pagination in the audit findings.

Run TypeScript.

STEP 6 — ERROR AND EMPTY STATES (REVISED)

Two distinct, user-visible empty states are required — these are
biologically and technically different situations and must not be
collapsed into one generic message:

- Case A — identifier could not be resolved: RefSeq → UniProt mapping
  failed or was ambiguous (per Step 1's rule). Display: "Protein
  identifier could not be resolved." Do not attempt InterPro lookup
  in this case.

- Case B — resolved but no domains: UniProt mapping succeeded,
  InterPro returned zero domain annotations. Display: "No annotated
  domains available for this protein."

Additional cases:
- Non-human protein → confirm domain data actually returns.
- Malformed/partial source response (from either service) → graceful
  degradation, not a crash.
- Overlapping domains from different member databases → confirm all
  are displayed independently. Do NOT merge, truncate, or deduplicate.
