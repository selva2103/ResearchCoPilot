NON-NEGOTIABLE ARCHITECTURAL CONSTRAINTS

domainId is the canonical identifier everywhere internally (e.g.
Pfam PF00870 or InterPro IPR002117) — domainName is display-only,
never used as a key. Same discipline as GeneID, transcript accessions,
ClinVar VCV IDs, GO IDs, and pathway IDs throughout this project.

Never fabricate a domain, accession, or position range — if the
source doesn't provide exact boundaries, startPosition/endPosition
are null, not estimated.

No structure/3D visualization of any kind — that's Phase 5.8. This
phase lists domains (name, accession, position, source), nothing more.

No LLM-generated interpretation of domain function.

InterPro and Pfam are both freely available under open licensing (EBI)
— unlike KEGG, there is no licensing exclusion concern here, but
confirm current terms during Step 1 regardless, since terms can change.

If a new external host is required (InterPro/Pfam are not NCBI
Entrez family), build a new, minimal, dedicated client with its own
independent rate limiter — same pattern established in 5.6B, do not
force it through the NCBI-specific client.

Do NOT modify or merge with 5.4B's existing Region:/Site: role
chips — this phase's domain data is additive and structurally
separate, even though there may be conceptual overlap.

STEP 1 — MANDATORY AUDIT: REUSE-FIRST, THEN SOURCE SELECTION

Do this before writing any implementation code. Write findings to
PHASE-5.7A-AUDIT-FINDINGS.md, including a decision-log table.

1. Reuse-first check: Inspect whether the GenPept FEATURES data
already fetched for 5.4B's role chips (Region:/Site: extraction)
includes position/coordinate information (GenBank feature table
entries always carry a location range) and whether these regions
already correspond to recognizable domain families. Compare a
representative protein (e.g. NP_000537.3 / TP53) against InterPro's
own listing for the same protein — same "presence vs. completeness"
comparison discipline used in 5.6A.


2. Decision rule (strict): reuse GenPept FEATURES only if they
provide canonical, stable, accession-bearing domain identifiers
(e.g. an actual Pfam/InterPro ID, not just a free-text region name)
together with reliable residue boundaries. Free-text region names
without a real accession do NOT qualify, even if they look
domain-like — in practice GenPept FEATURES rarely carry canonical
domain IDs, so expect InterPro to be the likely outcome unless proven
otherwise. If FEATURES don't meet this bar, use InterPro's REST API
(which aggregates Pfam, PROSITE, SMART, and others under one
canonical accession system — prefer InterPro over calling Pfam
directly, since InterPro's own accessions are the more stable
canonical layer).


3. Confirm InterPro's API can be queried using data already available
(protein accession — NP_/XP_ — is the natural key; confirm this
works directly without requiring UniProt mapping, unlike Reactome's
situation in 5.6B). Confirm this using live requests rather than
relying solely on documentation. Record the exact tested RefSeq
accession(s) and the observed response (status, key fields returned)
in PHASE-5.7A-AUDIT-FINDINGS.md. If direct RefSeq protein accession
support is NOT available and an additional accession-mapping layer
(e.g. UniProt mapping) would be required to use InterPro: STOP and
document the incompatibility in PHASE-5.7A-AUDIT-FINDINGS.md instead
of introducing new mapping infrastructure without approval — this is
an Architecture Escalation Rule case, identical in kind to 5.6B's
Reactome/UniProt situation.


4. Confirm non-human protein coverage (test with a mouse protein, e.g.
TP53's mouse ortholog's protein accession) — domain data is sequence-
based, not species-restricted, so this should work natively; confirm
it does.


5. Document the final decision with comparative evidence.



Do not proceed to Step 2 until this is complete and documented.

STEP 2 — PROTEINDOMAIN DATA CONTRACT

interface ProteinDomain {  
  domainId: string;              // canonical — e.g. "PF00870" or "IPR002117"  
  domainName: string;            // display label only  
  source: "genpept-features" | "interpro"; // per Step 1's decision  
  startPosition: number | null;  // residue position on the protein  
  endPosition: number | null;  
  proteinAccession: string;  
  geneId: string;  
  organism: string;  
}

STEP 3 — RETRIEVAL SERVICE

Implement per Step 1's decision:

If GenPept FEATURES: parser addition only, reusing 5.4B's existing
GenPept fetch (no new NCBI call).

If InterPro: new minimal client, completely independent: HTTP
client, rate limiter, and cache namespace (mirroring exactly how
5.6B's Reactome/WikiPathways client was isolated from the NCBI
client) — new cache namespace (e.g. proteindomain:{proteinAccession}),
same three-tier cache separation. Cache keys MUST be based on
proteinAccession only — do not cache by protein name, gene symbol, or
domain name. If the selected InterPro endpoint paginates results,
retrieve all pages before normalization — do not silently truncate
the domain list to a single page. Document the observed pagination
behavior (page size, total pages for a test protein) in the audit
findings.


Run TypeScript.

STEP 4 — PARSING AND NORMALIZATION

Do not deduplicate by domainId, domainName, or position range unless the
source explicitly returns duplicate records with the same accession,
coordinates, and source. Distinct signatures from different member
databases are biologically valid and must be preserved.

Map source data into ProteinDomain[]. Deterministic failure handling:
skip malformed entries individually, preserve the rest. Never fabricate
positions when a source provides a name but no coordinates — leave them
null rather than guessing.
